Provenance you can check without asking us

A ledger is only worth building if its claims survive an adversary reading them

sanctum-chain records cryptographic provenance — which key signed what, on which device, at which point in time — in an append-only log, publishes a signed tree head, and anchors that head to a public chain. Authority comes from a hardware signature the contract verifies, never from the address that paid the gas.

Why this is the first section. An earlier version of our timestamping site described open receipts, hardware-attested signing and a public log endpoint as available, while its own transparency page — four clicks away — correctly said all three were unbuilt. For a product whose only value is that its claims hold up under checking, that is the most expensive contradiction on the menu. So the tally sits above the pitch, the word blocked appears below without softening, and every line names the specific defect rather than gesturing at a roadmap.

The authority model

The signature is the authority. The chain is only the witness.

Most on-chain permission systems answer 'who may do this?' with 'whichever address sent the transaction.' That collapses the key that proves an identity into the key that pays a fee, and the fee-paying key lives in a hot wallet.

01

Authority lives in hardware

A registration records a P-256 public key held on a hardware token. Every later operation is checked against a signature from that key. The token cannot export it, so authority cannot be copied off the device — only exercised on it.

02

The deployer is a relayer

Because the contract never consults the sending address for permission, the account that deploys and pays gas holds no protocol power after deployment. A disposable software key is the architecturally correct thing to deploy with, which is a claim worth making precisely because it sounds careless.

03

Append-only is enforced, not promised

The event table refuses updates and deletes at the database level. An operator with full credentials still cannot rewrite history through the normal path, so the log’s integrity does not rest on the discipline of whoever holds the password.

What this does not give you. A single operator runs the validator set today. Reputation scoring is implemented and recorded, but with one validator it is instrumentation rather than consensus — so the correct description of the trust model right now is a transparent log you can audit, not a decentralised one you need not trust. Signed-tree-head signing also fails closed when the hardware token is absent, which means a cloud-only deployment currently produces no signatures at all. That is the right failure direction, and it is a real deployment constraint.

Mechanics

From an event to something a stranger can verify

Four steps, each of which produces an artefact that outlives the step.

Step 01

Record

An event lands in the append-only log with its tenant, its object identifier provenance and, where a hardware token was involved, the attestation that proves which device held the key.

Step 02

Accumulate

Events become leaves in a Merkle tree. Any single event can later be proven to belong to the tree with a path of hashes, without disclosing any other event in it.

Step 03

Sign

The tree head is signed by a key held on hardware. The signature says the operator committed to this exact history at this exact size — a later history that omits an event will not match.

Step 04

Anchor

The signed head is published to a public chain once every twenty-four hours, which fixes the history in time against a witness the operator does not control.

Why once a day, and not per event. Anchoring costs roughly 66 milliseconds; an overlay rekey costs 0.50 milliseconds — a hundred-and-seventy-seven-fold difference. Anchoring on every event would make the anchor the bottleneck for the whole system to buy precision nobody needs, so the design anchors rarely and rekeys constantly. A daily anchor bounds the uncertainty about when an event existed to one day, which is far tighter than any dispute over provenance actually requires.

Protocol authority is the registered P-256 key: the anchor contract verifies a signature against it through the precompile above and indexes it under the key id, so anchoring is permissionless and a compromised relayer cannot issue supply or move an anchored head backwards. What is deliberately absent. No provider endpoint token, no deployer key and no database credential appears in this bundle or in the environment that produced it. The browser talks to the ledger API; the ledger API talks to the provider. The build actively rejects a public URL containing a long opaque path segment, because that is the exact shape a leaked provider token takes.
